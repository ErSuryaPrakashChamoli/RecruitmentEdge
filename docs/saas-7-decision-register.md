# SaaS-7 — Decision Register

**For:** the project owner, Security, Operations and Engineering.

**Status:**
- Every decision in §1 is implemented on `feature/saas-7-scale-reliability`, branched from `e57ddaa` (SaaS-6).
- No commercial, legal or infrastructure policy was invented. Where a choice belongs to the owner — secrets manager, egress, monitoring vendor, backup policy, retention, limits, database scaling — the code ships a safe, configurable default and the question is listed in §2.
- Production readiness is tracked separately in `docs/saas-7-production-readiness.md`.

## 1. Decisions (implemented)

| ID | Decision | Why | Alternatives rejected | Revisit when |
|---|---|---|---|---|
| D-S7-01 | **Spatie's permission map is cached per tenant**: the permissions with the current tenant's roles only, under `<key>.<version>.tenant.<id>.<generation>`. A role change rotates its tenant's generation; a permissions-table change rotates the global version — each **twice**, when the change is made and again when its transaction ends (commit or rollback). With no tenant, the map holds no roles. | The global map held every tenant's roles: measured out of memory at 256 MB between 100 and 250 tenants (S7-01). Per tenant it no longer grows with the number of tenants (2,000 synthetic tenants: 9.9 KB each). The second rotation means a map rebuilt in between is never served after the change commits or is rolled back (MySQL race test; S7-26). | Raising `memory_limit`; disabling the cache (a query storm per request); a second authorisation system. | Redis (D-S7-O4) |
| D-S7-02 | **A job refused only because its tenant is paused leaves its work as it was** (`failed()` returns early on `TenantUnavailable`), so the SaaS-3 resume queues it again on reactivation. Any other failure still finalises the work. A unit architecture test requires the guard in every tenant job. | Paused-tenant work was finalised as Failed and never resumed (S7-02). | Resuming by re-dispatching from domain state (a second resume mechanism). | — |
| D-S7-03 | **The database cache store keeps its data on its own connection (`mysql_cache`); its locks stay on the business connection.** A lock that guards a decision made in a transaction is taken **before** the transaction opens (the applicant lock in the API and webhook intake). | Cache data (rate-limit counters, permission generations, the maintenance flag) must commit independently of business work. Locks must commit — or roll back — with the work they guard: on another connection a lock is released before that work is visible. The Phase D race showed two simultaneous API intakes of the same applicant creating two candidates with locks on `mysql_cache`; unique-job locks would also survive a rolled-back dispatch. Taking the applicant lock first means an intake never waits while holding row locks (the original S7-03 concern) and its snapshot starts after the previous intake committed. `ops:preflight` blocks either misconfiguration. | Everything on `mysql_cache` (first SaaS-7 attempt: duplicate applicants); everything on the business connection (counters and generations join transactions); Redis (not available — D-S7-O4). | Redis (D-S7-O4) |
| D-S7-04 | **The scheduler queues a frequent tenant task only for tenants holding something it could act on** (`TenantWorkProbes`: a superset, ids only, one DISTINCT query per probe), enumerating tenants lazily. `--all-tenants` skips the probe. Tenant tasks are queued through a `PendingDispatch`, so their unique lock (per task and tenant) is taken. | About 57 jobs and 1.9 s of worker time per tenant per hour were mostly no-ops. The SaaS-1 dispatcher bypassed the job's unique lock (`Bus::dispatch`), so a backed-up queue gained one more copy per tenant on every tick (found by the Phase D race). | Per-tenant schedules; dropping the frequent tasks. | — |
| D-S7-05 | **`tenants:run --all --budget=<s>`**: no tenant is started once the budget is spent; the next run resumes after the last tenant (a cursor in the shared cache). **Each tenant is re-read, with a shared lock, just before its work runs.** | A long pass outlived its overlap lock; a tenant suspended after its chunk was read still got that pass's work (up to the whole pass). The shared lock makes an in-flight suspension or closure wait and then count. | Re-checking without a lock (proven insufficient by the race); one queued job per tenant (would need new jobs per task). | — |
| D-S7-06 | **The health check computes every tenant's problems in one grouped pass.** Platform-level problems become platform events; the critical ones are mailed at once (`sendNow`), never through the queue being reported on. A scheduled task that failed, or has not finished for three of its runs, is a problem. | A full scan per tenant every five minutes; platform alerts reached nobody (S7-04). | A monitoring vendor (D-S7-O6). | D-S7-O6 |
| D-S7-07 | **Per-tenant integration budgets and a circuit** (`api.webhooks.tenant_deliveries_per_minute`, `tenant_inbound_per_minute`, `circuit_failures`, `circuit_cooloff_seconds`): past the budget, or while an endpoint's circuit is open, work is **deferred** (still due, no attempt counted) and the sweep sends it later. A deferral rewrites only a delivery that is still due. | One tenant's integrations must not occupy the shared worker. Nothing is dropped. The due-only rewrite keeps the retry schedule of an attempt another worker just made (Phase D race). | Per-tenant queues or workers (D-S7-O5); dropping excess work. | D-S7-O11 |
| D-S7-08 | **`DeliverWebhook` is unique per delivery until it starts.** | The five-minute sweep re-queued every due delivery, multiplying a backlog. | — | — |
| D-S7-09 | **Queues:** payment-provider events on `billing` (priority worker); no tenant task on `default`; each tenant task times out below its own worker's `--timeout` (110 s, 290 s on long queues); Filament export chunks retry for one hour, not a day; queued mail and notifications declare tries, backoff and `failed()`. | S7-08, S7-09. | New workers (no evidence they are needed — D-S7-O5). | D-S7-O5 |
| D-S7-10 | **`/health/live`** (no dependency) and **`/health/ready`** (database, cache, storage; public payload `{"status": …}` only, details with the health token). The compose `app` healthcheck uses readiness. | Liveness and readiness are different questions; the public payload reveals nothing. | `/up` only. | D-S7-O6 |
| D-S7-11 | **`ops:preflight`** validates the production configuration (key, debug, HTTPS, secure cookie, shared cache, cache data and lock connections, async queue, real mailer, database password, tenant-scoped permission cache); blockers fail. The entrypoint refuses to start production on a blocker; `PREFLIGHT_ENFORCE=false` is the one documented override. Messages never carry a configured value. | S7-05: nothing validated the configuration. | Validating at request time. | D-S7-O12 |
| D-S7-12 | **`audit:protect install`** adds two triggers making `audit_logs` append-only in the database (UPDATE and DELETE refused, whatever issues them). It is a **privileged** step: MySQL with binary logging refuses `CREATE TRIGGER` to an ordinary user. Preflight warns while it is not installed; `ops:verify-integrity` reports it. | S7-12 / S5-R1: immutability was application-only. Foreign-key `SET NULL` actions do not fire triggers; the tenant purge retains audit rows. | Revoking grants only (needs a separate migration user — D-S7-O8); log shipping (infrastructure). | D-S7-O8 |
| D-S7-13 | **`security:reencrypt`** rewrites every value of every encrypted column under the current `APP_KEY` (compare-and-set; `--dry-run`; unreadable values counted and fail the command). A registry test keeps the column list equal to the models' encrypted casts. | S7-11: a previous key could never be retired. | A vault with envelope encryption (D-S7-O1). | D-S7-O1 |
| D-S7-14 | **`ops:verify-integrity`**: foreign-key orphans (MySQL and SQLite), tenancy violations, pending migrations, audit protection — for after a restore. | A restore loaded with foreign-key checks off is not proven by MySQL itself. | — | D-S7-O7 |
| D-S7-15 | **`ops:migrate`**: the migrations under a MySQL named lock per database (`GET_LOCK`), used by the compose `migrate` service and `RUN_MIGRATIONS`. A second run waits, then finds nothing pending. | Two concurrent runs would apply the same migration twice (a backfill twice is corruption). `migrate --isolated` keeps its mutex in the cache tables, which do not exist on a fresh database. | `--isolated`; relying on the single compose service. | D-S7-O12 |
| D-S7-16 | **Observability:** `api.request` (route, status, duration, credential id), `db.slow_query` (SQL above `DB_SLOW_QUERY_MS`, never bindings), integration health in `/health/queue`; redaction of webhook secrets, API tokens (key id kept), bcrypt hashes, OAuth tokens, JWTs and LibreOffice stderr. | S7-10; operators need signals without secrets. | A monitoring vendor's agent (D-S7-O6). | D-S7-O6 |
| D-S7-17 | **Four tenant-led indexes**, each with an EXPLAIN on a copy with two 100k tenants and a small one: `candidates (tenant_id, updated_at)`, `candidate_applications (tenant_id, updated_at)`, `candidate_stage_histories (tenant_id, created_at)`, `audit_logs (tenant_id, created_at)`. Two measured candidates were **not** added. | Rule: no index without a demonstrated query. Results: `docs/saas-7-capacity-plan.md` §3. | `(tenant_id, current_stage, id)`: 7.1 → 0.7 ms for a small tenant only, milliseconds in absolute terms; `(tenant_id, status, id)`: no gain. `db.slow_query` will show if that changes. | D-S7-O13 |
| D-S7-18 | **Deployment:** trusted proxies from `TRUSTED_PROXIES` (unset: no forwarded header is believed); the maintenance flag in the shared cache; workers run with `--force` so a release drain still empties the queues; SMTP timeout 30 s. | S7-05; a recreated container stayed up during maintenance. | — | D-S7-O3, D-S7-O12 |
| D-S7-19 | **Security headers stay on the public pages** (the approved scope, E-03); the panels are not changed. | An existing test asserts the approved scope; the panels rely on `SameSite=Lax` cookies. Recorded as an Info finding. | Extending headers to the panels without a review of Filament's inline scripts. | Penetration test |
| D-S7-20 | **Tenancy fixes:** `AccessReview`'s open-handoff filter uses the tenant-scoped model; the handoff job's unique id carries its tenant. | S7-06 (one-bit cross-tenant disclosure), S7-07 (cross-tenant availability). | — | — |
