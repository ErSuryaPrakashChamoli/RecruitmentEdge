# SaaS-2 — Decision Register

**For:** the project owner, Security, Operations and Engineering.

**Status:**
- Every decision below is implemented on `feature/saas-2-identity-access`, branched from `0e8d865` (SaaS-1A).
- Each was taken inside the SaaS-2 brief. Each one can be revisited; the "Revisit when" column says when.
- Open items need an owner (§2).

## 1. Decisions (implemented)

| ID | Decision | Why | Alternatives rejected | Revisit when |
|---|---|---|---|---|
| D-S2-01 | **The identity (`users`) is global and holds only what is the person's own everywhere**: name, email, password, MFA, sessions, theme, and the platform identity lock (`disabled_at`). | Brief §3, §6. One person, one identity, any number of tenants. | Copying a user per tenant (duplicate identities, divergent passwords). | Federated identity (SSO/SCIM) arrives: it attaches to the same row. |
| D-S2-02 | **The tenant membership is the authoritative access relationship.** It holds the access state (active / suspended / revoked, with who, when, why, source and the roles a revocation removed), the employee record in that tenant, and the default-tenant preference. | Brief §7, §8. One tenant's decision must never change the person's access to another tenant. This removes SaaS-1's "employing tenant" workaround (D-S1-11, D-S1-13). | Keeping access on the identity (one tenant suspends everyone); a separate access table (two sources of truth). | — |
| D-S2-03 | **Membership states reuse the existing `AccessState` terminology: Active, Suspended, Revoked.** "Invited" is the pending `TenantInvitation`, never a membership row. The SaaS-1 `TenantMembershipStatus` enum is folded into `AccessState`. | Brief §7: "use the project's existing terminology". A membership exists only once someone has accepted. That way no half-made row can ever be mistaken for access, and only Active grants anything. | An `invited` membership state, whose fail-safety would depend on every check remembering to exclude it. | — |
| D-S2-04 | **`users.employee_id`, `access_status`, `access_changed_at/by`, `access_reason`, `access_source` and `revoked_roles` are moved to the membership (expand → backfill → contract) and dropped.** | A stale tenant-less copy left on the identity would be a silent trap. Code that still names the old columns now fails loudly on MySQL, and an architecture test stops it from coming back. | Keeping the columns "for compatibility", which would be read by mistake. | — |
| D-S2-05 | **`$user->employee_id`, `$user->employee`, `$user->access_status` and `$user->revoked_roles` are read from the membership of the current tenant.** `employee()` is a tenant-scoped `HasOneThrough`. `Employee::user()` goes through the membership. The values cannot be written on the identity (writing them throws). | About 250 existing call sites keep asking "this person's employee here" and get this tenant's answer, with no rewrite of domain services (brief §41). Outside a tenant the answer is null, so it fails closed. | Rewriting every call site to take a tenant argument. | — |
| D-S2-06 | **Access decisions are per tenant.** `StaffAccessService::permits()` answers for the current tenant: Active membership, usable tenant, identity not disabled, and no employment block there. It refuses when there is no tenant. `accessibleTenants()` confirms each candidate tenant inside that tenant. | A separation or an inactive employment in one tenant must close that tenant only. | One identity-wide gate. | — |
| D-S2-07 | **Sessions end only when no tenant is left to the identity.** Otherwise every request re-checks the membership of the URL's tenant, Livewire updates included. | Signing a person out of Tenant B because Tenant A suspended them is a cross-tenant effect. Per-request validation closes the suspended tenant immediately. | Revoking every session on any membership change. | — |
| D-S2-08 | **A tenant manages global credentials (password, email change, MFA reset, sign-out-everywhere, the name) only for an identity that belongs to that tenant alone.** | Otherwise Tenant A could set the password of a person who also belongs to Tenant B and sign in there: a cross-tenant account takeover. It becomes reachable as soon as an identity can join a second tenant. | Letting the "employing tenant" manage them (it would still open the other tenants). | Enterprise-managed identities (verified-domain ownership, SaaS-5/6). |
| D-S2-09 | **Invitations are the only way into a tenant.** Administrators invite (they no longer create logins with a password). Conversion and rehire invite with the base role. The identity is created only when an invited person accepts and the address has no identity yet. | Brief §13–15 and S1-01. The outcome is identical whether or not the address is known on the platform, so nothing is enumerated. The person proves they own the address and chooses their own password. | Creating a login directly for a new address and inviting only existing ones (the difference reveals which is which). | — |
| D-S2-10 | **Invitation tokens are 64 random characters; only their SHA-256 is stored. The link leaves the URL at the first request** (the hash is kept in the session). A resend replaces the token. | Brief §13/§15: never store or log a token in plaintext. The token appears once in a web-server access log line and nowhere else. | Signed URLs carrying the invitation id (replayable until expiry; reveal the id). | — |
| D-S2-11 | **An invitation is accepted inside its own tenant, found from the token, never from the URL.** The acceptance locks the invitation (conditional updates), serialises one identity's acceptances on its user row, reads the tenant under a lock, and re-checks what was promised: the roles still exist, the inviter can still grant them, and the employee record is still current and unlinked. | Brief §13: atomic; no replay, race, wrong identity, wrong tenant, or suspended or cancelled tenant. All of these are proven on MySQL (`tests/Concurrency/IdentityRaceTest.php`). | Trusting the invitation as created. | — |
| D-S2-12 | **An invitation never lifts a suspension.** It re-activates a revoked membership with the invited roles only. An already-active membership is never changed by a stale invitation. | A suspension is an access decision of the tenant; restoring it goes through StaffAccessService. | Re-activating any membership. | — |
| D-S2-13 | **No silent default tenant.** Filament's fallback to "the first tenant" is removed (`StaffFilamentManager`). The default is the person's chosen membership while it is accessible, or the only accessible tenant. Otherwise the person sees an organisation chooser (`/admin/organisations`). | Brief §11: "default tenant ≠ authorisation"; never switch someone silently when their default became inaccessible. | Filament's first-tenant fallback. | — |
| D-S2-14 | **Entering or switching a tenant is audited once per change, in the tenant entered.** The source tenant is written only to the platform log. | Brief §27. Telling Tenant B which other tenant the person came from would leak membership across tenants. | Recording "from" in the destination tenant's audit. | SaaS-5 platform audit console. |
| D-S2-15 | **Tenant MFA policy: `tenants.mfa_required`, changed by the tenant's access administrators (`users.access.manage`) with a reason, and audited.** The requirement applies to the identity everywhere: required by any active membership means required at every sign-in (stricter-of). | Brief §18: "MFA requirements must never be weakened by switching tenants". It completes D-S1-12. | A per-tenant requirement checked only inside that tenant, which could be bypassed via tenant-less pages or switching. | Per-tenant MFA methods, or step-up per tenant. |
| D-S2-16 | **Tenant-scoped relations (`roles`, `permissions`, `employee`) loaded in one tenant are never reused in another** (`User::relationLoaded` / `setRelation`). Access memos are invalidated by any tenant or membership write. | Brief §25. Spatie's loaded `roles` relation outlived a tenant switch on the same object (found in SaaS-1 tests, which worked around it with `unsetRelation`). | Relying on callers to call `unsetRelation`. | spatie supports per-team relation caching. |
| D-S2-17 | **Role changes lock the membership and re-check it**, so a role granted at the moment of a revocation never lands on the revoked membership. | Found while writing the role-update race test. It granted no access (revoked means no permission), but it left an inconsistent state. | — | — |
| D-S2-18 | **Platform plane: `platform_operators` (administrator / support / compliance), granted on the command line, audited in the platform stream, and consulted by nothing in the tenant plane.** | Brief §19: a platform operator is not a member of every tenant; there is no `tenant_id = NULL` meaning "all tenants". | A global role in spatie (it would mix with tenant roles); a `tenant_id IS NULL` membership. | SaaS-5 platform panel. |
| D-S2-19 | **Support access foundation: `support_access_grants`, created by the tenant's own `users.access.manage` holders for one active support operator.** Grants are time-bound (at most `identity.support.max_minutes`, default 480), revocable and audited. **They open nothing in SaaS-2.** | Brief §20: explicit, time-bound, auditable, tenant-specific, revocable, and never "log in as". The console that honours a grant is SaaS-5. | A global impersonation shortcut. | SaaS-5 support console. |
| D-S2-20 | **Platform identity lock (`users.disabled_at`)**, set by platform staff on the command line (`identity:disable`). It closes every tenant and ends every session, and leaves each tenant's own decisions untouched. | Brief §26: "user disabled". A compromised account is a platform decision, not a tenant's. | Using a tenant's suspension for it. | SaaS-5 platform panel. |
| D-S2-21 | **Neutral answers everywhere an address could be probed:** "Forgot password" (same message for sent, unknown and throttled addresses, and for an identity with no tenant); self-service and administrator email changes (a taken address simply gets no link); inviting; conversion. | Brief §15/§17, S1-01. Filament's defaults said "We can't find a user with that email address", or "already taken". | — | — |
| D-S2-22 | **Disclosure accepted (Low, S2-05):** the holder of a valid invitation link learns whether the invited address already has an identity (sign in vs create account). | The link is a secret sent to that mailbox. The holder is the address's owner, or has the owner's mail. | Making new people go through "Forgot password" first (more steps for everyone, no real gain). | — |
| D-S2-23 | **Disclosure accepted (Low, S2-06):** a tenant's administrator sees that one of their own members also belongs to another organisation (the credential fields are read-only, with the reason). | Needed to explain why they cannot reset that person's password. Which organisation is never shown. | Hiding the fields without a reason (support burden). | — |
| D-S2-24 | **An identity that can enter no tenant is signed out** (previously a 403 page inside a still-valid session). | Brief §26: no stale session after the last tenant closes, including when the tenant is cancelled or the identity is disabled. | — | — |
| D-S2-25 | **The fresh-install CHRO seed gets its membership.** | Pre-existing defect: in SaaS-1 the seeded administrator could reach no tenant on a fresh install. | — | — |
| D-S2-26 | **No new dependency.** OIDC, SAML, SCIM, passkeys and service accounts attach later to the same `users` row (a federated identity table) and to memberships (provisioning) without replacing them. | Brief §30/§42. No speculative interfaces were added. | — | SaaS SSO phase. |
